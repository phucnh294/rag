Module 02 · LLM Models

LLM Model là gì?

LLM (Large Language Model) là một file khổng lồ chứa hàng tỉ con số — gọi là parameters (tham số). File này được "huấn luyện" trên lượng text khổng lồ để học cách dự đoán từ tiếp theo. Khi bạn nghe "GPT-4", "Claude", "Llama" — đó là các LLM model khác nhau, được train khác nhau, có kích thước khác nhau.

Model không phải là phần mềm — nó là "bộ não" đã học xong

Hãy tưởng tượng thế này: model giống như một bộ não đã đông lạnh sau khi học. Bản thân nó không chạy được. Bạn cần một engine (động cơ) để nạp bộ não đó vào và cho nó suy nghĩ.

🧠
Model (weights / trọng số)
Là file chứa hàng tỉ số đã học. Ví dụ: llama-3.1-8b có 8 tỉ parameters. Nó "tĩnh" — không tự chạy được.
⚙️
Engine (inference engine)
Phần mềm nạp model vào bộ nhớ và chạy tính toán để sinh ra câu trả lời. Ví dụ: Ollama, vLLM, llama.cpp.

Module 02 · Parameters

Parameters — "Kích thước não" của model

Khi bạn thấy tên model có "8B", "70B", "405B" — đó là số parameters (tỉ tham số). Đây là số lượng con số mà model đã học được. Nhiều parameters hơn thường = model thông minh hơn, nhưng cũng = nặng hơn, chậm hơn, tốn RAM/GPU hơn.

Con số "B" nghĩa là gì?

1B
1 tỉ parameters
= ~1–2 GB RAM
8B
8 tỉ parameters
= ~5–6 GB RAM
70B
70 tỉ parameters
= ~40 GB RAM
405B
405 tỉ parameters
= cần cluster GPU
Quy tắc thực tế cho máy local: Máy laptop thường của bạn (16GB RAM) chạy tốt model 7B–8B. Máy có GPU 24GB chạy được 14B–32B. Model 70B+ cần máy trạm hoặc nhiều GPU. Đây là lý do các model nhỏ như Llama 3.1 8B rất phổ biến cho dev local.

Nhiều parameters có luôn tốt hơn không?

Không hẳn. Đây là điều nhiều người hiểu nhầm:

✅
Model lớn (70B+) giỏi hơn ở...
Reasoning phức tạp, kiến thức rộng, hiểu ngữ cảnh tinh vi, ít "ảo giác" hơn, viết code khó.
⚡
Model nhỏ (7B–8B) thắng ở...
Tốc độ nhanh, chạy được local, chi phí thấp, đủ tốt cho task đơn giản như phân loại, tóm tắt ngắn.

Một model 8B được fine-tune tốt cho một nhiệm vụ cụ thể có thể vượt model 70B ở nhiệm vụ đó. Chọn model là bài toán cân bằng: độ thông minh cần thiết ↔ tốc độ ↔ chi phí ↔ phần cứng bạn có.

Quantization — "nén" model để chạy nhẹ hơn

Bạn sẽ thấy các tên như llama3.1:8b-q4. Chữ q4 là quantization — kỹ thuật nén các con số từ độ chính xác cao (16-bit) xuống thấp hơn (4-bit) để model chiếm ít RAM hơn, chạy nhanh hơn, đổi lại mất một chút chất lượng.

Module 02 · Inference Settings

Các setting tác động đến câu trả lời

Cùng một model, cùng một câu hỏi — nhưng bạn có thể điều chỉnh cách nó trả lời qua vài thông số khi gọi. Đây không phải là parameters của model (đã cố định sau khi train), mà là inference settings — cài đặt lúc chạy. Quan trọng nhất là Temperature.

Thử ngay — Kéo Temperature xem câu trả lời đổi thế nào

TEMPERATURE 0.7
0.0 — Chính xác, lặp lại 2.0 — Sáng tạo, ngẫu nhiên
Prompt: "Viết một câu về con mèo"
Quy tắc chọn Temperature: Việc cần chính xác (trích xuất dữ liệu, trả lời factual, code) → dùng 0.0–0.3. Việc cần sáng tạo (viết marketing, brainstorm, story) → dùng 0.7–1.2. Temperature = 0 không hẳn "luôn giống hệt" nhưng gần như deterministic.

Các setting quan trọng khác

🎲 Top-p (nucleus sampling)
Giới hạn model chỉ chọn trong nhóm từ có xác suất cộng dồn tới p. top_p=0.9 = chỉ xét 90% khả năng cao nhất. Thường để cùng temperature.
🔢 Top-k
Chỉ xét k từ có xác suất cao nhất ở mỗi bước. top_k=40 = chỉ chọn trong 40 từ hàng đầu. Lọc bớt lựa chọn "rác".
📏 Max tokens
Giới hạn độ dài câu trả lời tối đa. Đặt để tránh model viết lan man và kiểm soát chi phí (vì tính tiền theo token).
🚫 Stop sequences
Chuỗi ký tự báo model dừng lại. Ví dụ dừng khi gặp "\n\n" hoặc "###". Hữu ích khi muốn output có cấu trúc.

System Prompt — cách mạnh nhất để định hình model

Ngoài các con số, thứ tác động lớn nhất đến hành vi model là system prompt — chỉ dẫn ban đầu bạn đặt cho model. Đây là nơi bạn nói "Mày là chuyên gia tài chính, trả lời ngắn gọn bằng tiếng Việt".

Cùng model, khác system prompt = khác hoàn toàn: Một Llama 3.1 8B với system prompt "Bạn là trợ lý pháp lý cẩn thận" sẽ hành xử rất khác với cùng model đó nhưng prompt "Bạn là copywriter vui nhộn". Bạn sẽ học sâu về prompt engineering ở các module sau.
Module 02 · System Architecture

Bên trong một hệ thống LLM có gì?

Khi xây dựng ứng dụng AI thực tế, LLM model chỉ là một mảnh. Một hệ thống hoàn chỉnh thường có hai thành phần cốt lõi: LLM Engine (chạy model) và Vector Data Store (lưu kiến thức). Hiểu hai cái này là nền tảng cho toàn bộ phần RAG sắp tới.

👤
User Query
Câu hỏi của người dùng
→
🗄️
Vector Store
Tìm kiến thức liên quan
→
⚙️
LLM Engine
Model sinh câu trả lời
→
💬
Response
Trả lời cho user

Thành phần 1 — LLM Engine (động cơ chạy model)

Là phần mềm nạp model vào RAM/GPU và thực hiện inference (suy luận). Nó nhận input, chạy hàng tỉ phép tính, trả về token. Không có engine, model chỉ là file chết.

Ollama
Dễ nhất cho dev local. Một lệnh là chạy được model. Chúng ta sẽ dùng cái này.
vLLM
Engine production, tối ưu tốc độ cho server phục vụ nhiều user cùng lúc.
llama.cpp
Engine nền tảng, chạy được cả trên CPU. Ollama build trên nó.

Thành phần 2 — Vector Data Store (kho kiến thức)

LLM model có kiến thức "đóng băng" từ lúc train, và không biết dữ liệu riêng của bạn (tài liệu công ty, database nội bộ). Vector store giải quyết việc này: nó lưu tài liệu của bạn dưới dạng vector số, để khi user hỏi, hệ thống tìm đúng đoạn liên quan và đưa vào cho model.

📥
Cách hoạt động
Tài liệu → chia nhỏ (chunk) → biến thành vector (embedding) → lưu vào vector DB. Khi hỏi, câu hỏi cũng thành vector và tìm các vector gần nhất.
🗃️
Vector DB phổ biến
pgvector (PostgreSQL), Chroma, Qdrant, Weaviate, Pinecone. Chúng ta sẽ dùng pgvector ở Module 5.
Đây chính là RAG (báo trước Module 4–5): Kết hợp LLM Engine + Vector Store = kiến trúc RAG (Retrieval-Augmented Generation). Model không cần "nhớ" mọi thứ — nó chỉ cần được đưa đúng thông tin vào đúng lúc. Module này bạn chỉ cần hiểu hai thành phần tồn tại và vai trò của chúng.
Module 02 · Lab · Ollama

Ollama — Chạy LLM open source trên máy của bạn

Ollama là công cụ giúp bạn tải về (pull) và chạy các model open source ngay trên máy local chỉ bằng vài lệnh. Không cần API key, không tốn tiền, dữ liệu không rời khỏi máy. Đây là công cụ nền tảng chúng ta dùng xuyên suốt khóa học.

Bước 1 — Cài Ollama

Tải tại ollama.com cho Windows / Mac / Linux. Sau khi cài, mở terminal và kiểm tra:

terminal
$ ollama --version
ollama version 0.x.x

Bước 2 — Pull một model về máy

Dùng lệnh ollama pull để tải model. Model được tải từ thư viện của Ollama (giống như Docker Hub cho model):

terminal — pull model
$ ollama pull llama3.1:8b
pulling manifest
pulling 4.7 GB ████████████ 100%
success ✓

$ ollama pull qwen2.5-coder:14b # model giỏi code
$ ollama pull nomic-embed-text # embedding model cho RAG

Bước 3 — Chạy và chat với model

terminal — run
$ ollama run llama3.1:8b
>>> Giải thích RAG trong 1 câu
RAG là kỹ thuật cho LLM truy xuất tài liệu
liên quan trước khi trả lời, giúp câu trả
lời chính xác và cập nhật hơn.
>>> /bye

Bước 4 — Gọi Ollama qua API (quan trọng cho dev)

Ollama tự động chạy một server HTTP ở localhost:11434. Đây là cách bạn tích hợp model vào code:

terminal — API call
$ curl http://localhost:11434/api/generate -d '{
  "model": "llama3.1:8b",
  "prompt": "Xin chào",
  "stream": false
}'
{"response": "Xin chào! Tôi có thể giúp gì?", ...}

Chạy trực tiếp trên máy chỉ là bước làm quen. Ở lab thực tế, chúng ta đóng gói bằng Docker Compose — mỗi model là một service độc lập, có Dockerfile, env và volume riêng. Cách này giống môi trường production và dễ nhân bản khi thêm model.
Module 02 · Lab chính · Docker Compose

🧪 Lab Buổi 2 — llama3.1 trong Docker Compose

Mục tiêu: chạy model llama3.1 (8B) như một service Docker độc lập, có volume riêng, env riêng, entrypoint riêng. Model được pre-pull sẵn lúc build nên container khởi động là chạy ngay. Đây đúng pattern dự án thật — mỗi model một service.

Nguyên tắc thiết kế — mỗi service độc lập

🧩
Volume riêng
Mỗi model có volume lưu weights riêng (ollama_llama31_data). Thêm model khác không đụng nhau.
📄
Env riêng
.env.common (chung) + .env.ollama.llama3.8b (riêng model). Mỗi model một file env.
🚪
Entrypoint riêng
Tách file entrypoint.sh để sau này sửa logic khởi động mà không đụng Dockerfile.

Cấu trúc thư mục

project/
project/
├── docker-compose.yml
├── .env.common # biến chung (TZ, keep-alive)
├── .env.ollama.llama3.8b # tên model, host, cổng
├── DockerfileLlmLlama318b # pre-pull llama3.1 lúc build
└── entrypoint.sh # chỉ bật ollama serve

File .env — pattern common + model

.env.common
TZ="America/Chicago"
OLLAMA_KEEP_ALIVE=5m
.env.ollama.llama3.8b
OLLAMA_LLAMA31_HOST=host.docker.internal
OLLAMA_LLAMA31_HOST_PORT=11434
OLLAMA_LLAMA31_PORT=11434
OLLAMA_LLAMA31_MODEL=llama3.1:latest
Cách đặt tên biến: mỗi biến có prefix theo model (OLLAMA_LLAMA31_*) để khi có nhiều model chúng không đụng nhau. HOST_PORT = cổng publish ra host (mỗi model một cổng riêng, vd 11434, 11435, 11436...); PORT = cổng trong container, Ollama luôn nghe 11434.

DockerfileLlmLlama318b — pre-pull model lúc build

DockerfileLlmLlama318b
FROM ollama/ollama:latest
WORKDIR /root

# entrypoint tách riêng
COPY entrypoint.sh /usr/local/bin/entrypoint.sh
RUN chmod +x /usr/local/bin/entrypoint.sh

# Pre-pull model NGAY lúc build → bake vào image
RUN ollama serve & \
    server_pid=$! && \
    until ollama list >/dev/null 2>&1; do sleep 1; done && \
    ollama pull llama3.1:8b && \
    kill $server_pid

ENTRYPOINT ["entrypoint.sh"]

Model được nạp thẳng vào image lúc build. Dùng until ollama list để chờ server sẵn sàng thay vì sleep 5 — chắc chắn hơn. Lưu ý: model được hardcode ở đây (llama3.1:8b) vì lúc build chưa đọc được biến env; biến OLLAMA_LLAMA31_MODEL là để app biết gọi model nào lúc chạy.

entrypoint.sh — đơn giản, chỉ serve

entrypoint.sh
#!/bin/bash
set -e

echo "Starting Ollama server with pre-pulled model..."
exec ollama serve

Vì model đã bake sẵn lúc build, entrypoint chỉ cần bật server. Dùng exec để Ollama nhận signal đúng (dừng container sạch). File tách riêng nên sau này muốn thêm warmup hay pull thêm model thì sửa ở đây, không đụng Dockerfile.

docker-compose.yml — service llama31-8b

docker-compose.yml
services:
  llama31-8b:
    build:
      context: .
      dockerfile: DockerfileLlmLlama318b
    container_name: llama31-8b
    env_file:
      - .env.common
      - .env.ollama.llama3.8b
    restart: unless-stopped
    ports:
      - "${OLLAMA_LLAMA31_HOST_PORT}:${OLLAMA_LLAMA31_PORT}"
    volumes:
      - ollama_llama31_data:/root/.ollama
    deploy:
      resources:
        reservations:
          devices:
            - capabilities: [gpu] # dùng GPU nếu có

volumes:
  ollama_llama31_data:

Gọi model — chỉnh tham số để xem kết quả đổi

Model chạy ở localhost:11434. Gọi API với các tham số (nối lại Module ③ Settings) — đổi temperature, top_k, top_p và so sánh:

terminal — API call
$ curl http://localhost:11434/api/generate -d '{
  "model": "llama3.1:latest",
  "prompt": "Viết hàm tính giai thừa bằng Python",
  "stream": false,
  "options": { "temperature": 0.2, "top_k": 20, "top_p": 0.5 }
}'
{"response": "def factorial(n): ...", ...}
Bài tập chính: Gọi cùng một prompt với temperature: 0.0 ba lần, rồi temperature: 1.2 ba lần. So sánh: temperature thấp có ra kết quả giống nhau không? Cao thì sao? Đây là cách hiểu probability sampling bằng thực nghiệm.
App gọi model qua đâu? App container gọi model qua host.docker.internal:11434 (biến OLLAMA_LLAMA31_HOST + HOST_PORT) — đi ra host rồi vào cổng đã publish. Đây là pattern dự án thật: mỗi model một host port, app không cần biết model nằm ở đâu, chỉ cần đúng địa chỉ. Lưu ý: trên Linux (không phải Docker Desktop) cần thêm extra_hosts: ["host.docker.internal:host-gateway"].
Thêm model thứ hai: Copy pattern — tạo .env.ollama.mistral.24b với HOST_PORT khác (vd 11435) + DockerfileLlmMistral32 pull model khác + service mới với volume riêng ollama_mistral_data. Mỗi model hoàn toàn độc lập. Hỏi cùng một câu khó cho llama3.1 (8B) và mistral (24B), so sánh chất lượng và tốc độ — thấy rõ trade-off "thông minh vs nhanh" đã học ở Module ②.
