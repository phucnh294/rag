## TL;DR
- **What:** Replaced blind fixed-token chunking with structure-aware (markdown-boundary) chunking, added a hybrid search stage (vector + Postgres full-text, fused via Reciprocal Rank Fusion), and pushed the whole project to a new GitHub repo with secrets scrubbed.
- **Why:** Fixed-token chunking could slice a chunk mid-sentence or separate a heading from its content; pure vector search misses exact-keyword/acronym matches a full-text search would catch directly. Both were real gaps identified by inspecting the pipeline, not reported bugs.
- **Where:** `indexing/step3_chunking_strategy.py`; new `retrieval/hybrid/` package; `retrieval/step4_similarity_search.py`, `step6_reranking.py`, `retrieval_runner.py`, `step10_response.py`; `config/env_config.py`, `api/routes_chat.py`; `sql/03_hybrid_search.sql` (new) + `sql/migrations.py` (generalized); `ui/index.html`; repo root `.gitignore`/`README.md`/`.env.*.example` files.
- **Impact:** Both features implemented, migrated, and verified end-to-end against the live 7-doc PTO corpus with zero regressions on the two previously-fixed questions. Project is now version-controlled and pushed to `github.com/phucnh294/rag` (`main`, latest commit `22ef71b`).

## COMPLETED

- **Structure-aware chunking** (`indexing/step3_chunking_strategy.py`, full rewrite) — splits on markdown headings/paragraphs, packs blocks greedily to ~800 tokens without cutting mid-sentence, carries the last block forward as overlap, prefixes a chunk with its owning heading when it doesn't start under one, falls back to the old token-sliding-window only for a single oversized block. Verified: 3 local unit tests (small doc → 1 coherent chunk; large doc → 2 chunks with visible paragraph overlap + heading prefix; oversized single block → bounded at 800 tokens each). Live: re-uploaded all 7 corpus docs (`curl -F "file=@...md" [-F status=... -F area=...] http://localhost:8000/upload`), confirmed no duplicate rows, tags survived the upsert, both regression questions (PTO-days, PTO-request-process) still answer correctly.
- **Hybrid search** (`retrieval/hybrid/{query_builder,lexical,fusion}.py`, new package) — `query_builder.build_tsquery_text_martin` normalizes the question; `lexical.lexical_search_martin` runs `ts_rank(content_tsv, websearch_to_tsquery('english', %s))` against `rag_chunks`; `fusion.reciprocal_rank_fusion_martin` merges vector + lexical rankings by `chunk_id` (RRF, `k=60`). Wired into `retrieval_runner.py` as a conditional branch on `config.hybrid_enabled`, same shape as the existing `config.rerank_enabled` branch — no new orchestration framework (a "graph.py with nodes" was explicitly considered and rejected; see Context below).
- **`chunk_id`/`found_by` provenance threading** — `RetrievedChunk` (`step4_similarity_search.py`) gained both fields; `step6_reranking.py`'s rebuild now carries them forward (previously would have silently dropped them, the same class of bug status/area carrying-forward already had to fix once before).
- **Schema migration generalized to multiple files** (`sql/migrations.py`) — was single-file (`init_rag_db.sql`) hash-tracking; now iterates `_MIGRATION_FILES = ["init_rag_db.sql", "03_hybrid_search.sql"]`, each hash-tracked independently via a new `filename` column on `schema_migrations` (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS filename TEXT NOT NULL DEFAULT 'init_rag_db.sql'` — correctly backfills old rows, since every pre-existing row's hash *was* for that one file).
- **Toggle + response shape** — `HYBRID_SEARCH_ENABLED` env default (`false`) + per-request `ChatRequest.hybrid: bool | None`, `dataclasses.replace` override, identical pattern to `rerank`. Response gained top-level `"hybrid": bool` and per-chunk `"found_by": "vector"|"lexical"|"both"` in `retrieval_scores`. UI: "Hybrid search" checkbox, `found_by` badge in the debug panel, `· hybrid`/`· vector-only` message flag.
- **Rotating file logging** (`shared/logger.py`) — added a `RotatingFileHandler` (date-named file under `rag_pipeline/logs/`, 5MB cap, 5 backups) alongside the existing console handler, answering "where do logs get written" from earlier in the session. Not yet committed to git as its own line item — folded into the general code history, and `logs/` itself is gitignored (runtime output, not source).
- **Git repository created and pushed** — initialized at the workspace root (not just `session4-rag/`, per user's explicit choice), `.gitignore` excludes all real `.env*` files, `*.env.*.example` redacted templates added for every real env file (Gemini API key and DB password replaced with placeholders — verified via `git status --short | grep -i env` that only `.example` files were ever staged), root `README.md` written describing both projects (`session4-rag` main project, `module2` earlier exercise) plus setup instructions.

## CONTEXT THE NEXT SESSION CANNOT DERIVE FROM CODE

- **Decision:** hybrid search is added as two more conditional-branch calls directly inside `retrieval_runner.py`, NOT a new graph/node abstraction. **Reason:** the user's own proposed file structure included `retrieval/graph.py ← thêm 2 node`, which could have meant introducing a real LangGraph-style architecture. Explicitly asked via `AskUserQuestion` before planning; user chose to extend the existing flat step-file + runner pattern instead. **Rejected alternative:** a real `graph.py` with `StateGraph`-style nodes — would have been a genuine architectural fork coexisting awkwardly with the existing procedural pipeline, and nothing in `rag-structure.md` or any prior session doc suggested this pattern exists anywhere in the codebase (confirmed via explicit grep before asking).
- **Decision:** `sql/migrations.py` was generalized to support an ordered list of files rather than folding the hybrid-search DDL into the existing `init_rag_db.sql`. **Reason:** also explicitly asked via `AskUserQuestion` — user chose the multi-file approach to match the `sql/03_hybrid_search.sql` naming they'd already proposed, and it scales to future migrations without re-touching the base schema file each time. **Rejected alternative:** append the trigger/index/backfill statements directly into `init_rag_db.sql` — simpler (no `migrations.py` change needed) but was not what the user asked for.
- **Decision:** `HYBRID_SEARCH_ENABLED` defaults to `false` (unlike `RERANK_ENABLED`, which defaults to `true`). **Reason:** hybrid search is brand-new and unvalidated against real content that would prove its value (see NOT DONE above) — safer to ship opt-in. This was my own judgment call, not something the user was asked about; easy to flip if they want it on by default.
- **Trap:** the `_RERANK_CANDIDATE_POOL`/`_RERANK_TOP_N` constants in `retrieval_runner.py` were found at `10`/`10` when this session's work began, NOT `20`/`5` as recorded in the prior (09-02) handoff docs — someone/something changed them between sessions (the file was flagged "modified on disk since you last read it" mid-edit).
